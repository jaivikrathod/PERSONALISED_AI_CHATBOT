Architecture proposal · for review

From FAQ Search to a Tool-Calling Platform

Turn the fixed embed‑then‑answer pipeline into an orchestration loop where a per‑tenant tool registry — knowledge, structured data, and actions — is the only thing the model ever sees.

StatusDraft — decisions in §14
CodebaseTEMPSERVER · Django 5.2 / Channels
ScopeBackend architecture + schema

The FAQ pipeline you have is a correct implementation of the wrong shape. It decides before the model runs that this turn needs a vector search, and it can only ever produce one kind of answer. Everything below keeps the retrieval quality work you have already done and moves the decision one level up — to the model, constrained by a registry the backend owns.

§1 What breaks today

Grounded in the current code, not hypotheticals. questions/consumers.py is where the pipeline lives; vector_question/services.py holds embedding and generation.

#FindingWhereConsequence
F1 Retrieval is a full table scan in Python. _top_matches iterates every vectorized row and computes cosine in a Python loop over 384 floats. consumers.py ~4M interpreted float ops per message at 10k FAQs. No index is possible while embedding is a JSONField.
F2 The confidence threshold is almost certainly miscalibrated. CHAT_CONFIDENCE_THRESHOLD defaults to 0.90; MiniLM cosine for genuinely related sentence pairs typically lands in 0.45–0.75. settings.py Nearly every question escalates to a human. The bot looks broken and agents get flooded.
F3 Index and query text are asymmetric. Rows are embedded as "Question:\n…\n\nAnswer:\n…"; queries are embedded as the bare user sentence. services.py Depresses every score further, compounding F2. Two independent causes of the same symptom.
F4 Routing is hardcoded in the transport layer. The consumer decides handoff from a score comparison before any model call. consumers.py A greeting triggers a vector scan and can escalate. There is no place to add a second capability.
F5 No conversation history reaches the model. generate_answer(message, faq_pairs) receives one turn. services.py Follow-ups (“and under 80 lakh?”) are structurally impossible to answer.
F6 No chatbot entity. Configuration is implicit; the tenant key is company_id and every behaviour is global. schema Nowhere to hang per-bot tools, persona, model, or thresholds.
F7 There is no authentication. IsAdminOrManager returns true when the request carries ?user_type=Admin in the query string. Login issues no token. users/permissions.py Blocker Any browser can read or write any tenant's data by editing a URL.
F8 InMemoryChannelLayer. Groups exist only inside one process. settings.py Blocker Agent handoff silently fails the moment you run more than one worker.
Fix before anything else

F7 and F8 are not architecture, they are prerequisites. This design adds configurable outbound HTTP calls and cross-tenant structured data. Shipping either on top of a query-string permission check turns a demo weakness into a data breach. Real session tokens and a Redis channel layer are Phase 0, before any of §3 onward.

F2 and F3 are worth fixing this week regardless of this proposal — they are a one-line threshold change and a change to what text gets embedded, and they likely account for most of the current handoff volume.

§2 Target architecture

The change is structural, not additive: retrieval stops being a stage in a pipeline and becomes one of several capabilities the model may invoke. The loop is what is new.

Five planes

PlaneOwnsNew Django app
ConfigChatbots, knowledge sources, data sources + field registry, actions, credentials, compiled tool declarationsregistry
OrchestrationTurn lifecycle, context assembly, the model loop, budgets, degradationorchestration
CapabilityThree executors behind one interface: knowledge, structured, actioncapabilities
Datapgvector chunks, generic record store, adapter clients(within capabilities)
TrustTenancy binding, argument validation, egress control, rate limits, execution audit(cross-cutting middleware)

The transport layer (ChatConsumer) keeps only its socket job: accept a frame, resolve the session, hand the turn to the orchestrator, stream the result back. All the branching currently in receive() disappears.

Five clusters. Existing tables are marked — the migration is additive, and questions survives as an input format rather than the storage format.

Decision — parameters as rows and as schema

You listed tool_parameters as a table. Keep it for actions only, as action_parameters, because a no-code UI needs to edit parameters field by field. But tools.input_schema is the compiled artifact — the JSON Schema actually sent to the model, regenerated whenever the source rows or the field registry change. For STRUCTURED_SEARCH and KNOWLEDGE_SEARCH there are no parameter rows at all: the schema is derived from data_source_fields. One source of truth per tool type, one cached compilation.

Extending chat_message rather than adding a parallel table matters: the transcript an agent reads in the console and the transcript replayed to the model must be the same rows, or the two will drift and the agent will not see what the bot promised the customer.

§4 Tool registry

A tool row is a binding between a business-level name the model sees and an executor the backend owns. The model never learns which is which.

tool_typeconfiguration holdsinput_schema derived fromexecutor
KNOWLEDGE_SEARCH{source_ids: [..]} or empty for allfixed: query, optional top_khybrid retriever → pgvector + tsvector
STRUCTURED_SEARCH{data_source_id: 123}generated from data_source_fieldsquery compiler → validator → adapter
API_ACTION{action_id: 45}generated from action_parametersschema validator → egress-guarded HTTP client
HANDOFF{queue: "support", reason_required: true}fixed: reason, optional summaryexisting flag_agent_needed + agent group push
Decision — handoff becomes a tool

Today escalation is a side effect of a low similarity score. Make it request_human_agent, a tool the model calls when it judges it cannot help or the customer asks for a person — and keep a server-side safety net independent of the model: N consecutive turns with no successful tool result, an explicit “talk to a human” pattern match, or a tool-budget exhaustion all force the handoff regardless of what the model wants. Model judgement is better at the decision; the server rule is what stops a loop.

Compilation and caching

Declarations are compiled from config, not written by hand, and cached per (chatbot_id, schema_version). Invalidate on any write to tools, data_source_fields, or action_parameters. This matters for cost: declarations are re-sent on every model call in a turn, so a 6-tool bot pays roughly 400–900 tokens per round trip just to describe itself.

Compiled declaration — what the model actually receives
{
  "name": "search_available_listings",
  "description": "Search available property listings by location, budget,
                  size and type. Use when the customer describes what they
                  are looking for. Do not use for policies or company info.",
  "parameters": {

    "properties": {

No data_source_id, no operators, no field paths, no table names. The model sees a business capability; the backend keeps the mapping.

§5 Structured search

Your generic query JSON is the right internal contract. The proposal keeps it exactly — and does not ask the model to produce it.

Decision — flat parameters out, filter IR in

The model emits flat typed parameters; the compiler turns them into your filter IR. A generic filters: [{field, operator, value}] array asks the model to pick a field name, an operator, and a coerced value on every call, and JSON Schema cannot constrain any of them — {"field":"cost","operator":"under","value":"80 lakh"} is schema-valid and wrong three ways. A flat surface makes enums, ranges, and types enforceable in the declaration, so the whole class of error is caught before the call is made.

The IR stays the internal contract: adapter-agnostic, validated, logged, and the thing every executor consumes. Data sources that genuinely need OR-groups can opt into an advanced_filters parameter carrying raw IR — validated by exactly the same code path.

5.3 Adapters

  • records (default). Rows live in data_records.payload as JSONB. Filters compile to Django ORM KeyTextTransform lookups with an explicit cast per declared type. A GIN jsonb_path_ops index serves equality; B-tree expression indexes on numeric and date fields are created once when a data source is published, not per query.
  • rest_api. The IR maps to query parameters through a per-source template. Same validation, different sink. Subject to the egress rules in §7.
  • sql_readonly. A read-only connection to a tenant's own database with an allowlisted table and column set. Highest value, highest risk — defer past v1.
Trade-off — JSONB versus real columns

A single JSONB table means zero DDL per tenant and one code path, at the cost of casts on every filter. Per-source physical tables are faster and type-safe but require runtime DDL, which is an operational and security liability at tenant scale. Start with JSONB. It comfortably serves the tens-of-thousands-of-rows range that covers most tenants, and the adapter boundary means a specific large tenant can be moved to a materialized table later without touching the compiler, the validator, or the model.

5.4 Result shaping

What comes back is as much a design decision as what goes in — it is the model's context budget being spent.

Tool result
{
  "matched": 47,
  "returned": 10,
  "rows": [ { "title": "...", "city": "Ahmedabad", "price": 7500000,
              "bedrooms": 3, "ref": "PROP-1182" } ],
  "truncated": true,
  "relaxable_filters": ["max_price"]
}

Three things earn their place. matched lets the model say “47 match, here are 10” instead of implying it saw everything. truncated prompts it to offer narrowing rather than inventing a total. And on a zero-result query, relaxable_filters — computed by re-running the query with each filter dropped in turn — lets the model say “nothing at 80 lakh; the cheapest 3 BHK on SG Highway is 92” instead of a dead end. That is generic logic, no industry knowledge in it.

§6 Knowledge search

Same retrieval quality goals as today, reached differently — and now only when the model asks for it.

6.1 Retrieval

  1. Embed the query with the chunk's own embedding_model, normalized. Cache identical queries per chatbot for the session.
  2. Two recalls in parallel. pgvector HNSW cosine (top 30) and Postgres full-text over content_tsv (top 30). Vector alone is weak exactly where business content is strong: SKUs, policy names, plan tiers, error codes.
  3. Fuse with Reciprocal Rank Fusion (score = Σ 1/(60 + rank)). No score normalization needed between two incomparable scales, which is what makes RRF the right choice here.
  4. Apply the accept gate (6.2), then cap to top_k chunks and a hard token ceiling (~1200 tokens).

6.2 The relevance gate

Replacing a single global constant with three per-chatbot signals:

SignalPurposeStarting value
retrieval_floorDiscard obvious noise before fusioncosine ≥ 0.32
accept_thresholdBelow this, return zero chunks rather than weak onesfused rank-1 in top decile
margin_ruleIf rank 1 and rank 5 are indistinguishable, the query is probably off-domainΔ ≥ 15%
These numbers are starting points, not answers

Any threshold that is not measured against your own labelled data is a guess — which is how 0.90 got there. Build a fixture of ~50 questions per pilot tenant tagged answerable or not, and tune per chatbot against precision on the “not” set. Store the result in chatbots.policy. Ship the measurement harness in the same phase as the retriever, not later.

When nothing clears the gate the tool returns {"chunks": [], "reason": "no_relevant_content"}. This is the single most important behavioural difference from today: an empty result is a useful signal the model can act on — ask a clarifying question, try a different tool, offer a human — whereas three irrelevant FAQs are actively harmful, because a capable model will try to answer from them.

Keep the existing is_answer_found self-assessment, but treat it as a separate axis. Retrieval score answers did we find something; the model answers was it enough. Logging both against real conversations is what makes the thresholds tunable.

§7 Actions

Actions are the only capability that writes to the world, and the only one where a business user supplies a URL you will call. Both facts drive the design.

7.1 Confirmation for writes

Two-phase, enforced server-side rather than by prompt instruction. When requires_confirmation is set, the first invocation does not execute:

First call → not executed
{
  "status": "confirmation_required",
  "summary": "Create a lead for Priya Shah, +91 98250 11111",
  "confirmation_token": "cnf_9f2a…"
}

The model relays the summary, the customer agrees, and the model calls again with the token. Tokens are single-use, scoped to the conversation, bound to a hash of the validated arguments, and expire in five minutes — so a model that “confirms itself” or drifts on the arguments between calls fails closed.

7.2 Egress control

SSRF is the headline risk of this feature

“Business users configure an API URL” is a server-side request forgery primitive handed to your least-trusted input. Non-negotiables: per-company URL allowlist; DNS resolution before connect with the resolved IP checked against RFC1918, loopback, link-local and 169.254.169.254, then pinned for the request to close the TOCTOU gap; redirects disabled or re-validated per hop; HTTP(S) only; hard timeout; response size cap; no credentials forwarded cross-host.

7.3 Everything else

  • Secrets never enter the schema. Credentials resolve from credentials.secret_ciphertext at execution time and are injected into headers by the client. The model cannot see, request, or supply them, and they are redacted from tool_executions.
  • Idempotency. A key derived from (conversation_id, action_id, hash(arguments)) goes out as Idempotency-Key and is checked locally, so a retry after a timeout does not create two leads.
  • Rate limits at three scopes: per conversation per tool, per company per tool per minute, and a global egress ceiling.
  • Circuit breaker per action — after N consecutive failures the tool is withheld from the declaration list and the model routes around it instead of retrying into a dead endpoint.

§8 Orchestration loop

8.1 The turn

  1. Resolve conversation → chatbot → policy. Bind chatbot_id and company_id to the turn now; nothing downstream reads them from anywhere else, ever.
  2. If a human agent owns the session, skip the model entirely and deliver to the agent — the existing _live_agent_id check, unchanged and still first.
  3. Assemble context (§9). Load cached tool declarations.
  4. Call the model with history + declarations.
  5. No tool call → stream the reply, persist, done.
  6. Tool call(s) → validate (§10) → execute, in parallel when independent → append role='tool' messages → return to step 4.
  7. On budget exhaustion, degrade deliberately: one final model call with tools withheld and an instruction to answer from what it has or hand off.

8.2 Budgets

BudgetDefaultOn breach
tool_calls_per_turn4Withhold tools, force a final answer
model_round_trips3Same

A tool that times out returns a result, not an exception. The model handles “that lookup did not respond” far better than the orchestrator handles an unwind mid-turn, and the customer gets a sentence instead of a spinner.

8.3 Worked example — the multi-turn case

Turn 1
customer  "I want to buy a property in Ahmedabad"

model  → search_available_listings({ city: "Ahmedabad", limit: 10 })
tool   ← { matched: 312, returned: 10, truncated: true,
           rows: [...] }
model  → "We have 312 listings in Ahmedabad. To narrow it down —
          what's your budget, and how many bedrooms?"
Turn 2 — the follow-up
customer  "Under 80 lakh and 3 BHK, near SG Highway"

model  → search_available_listings({ city: "Ahmedabad", bedrooms: 3,
                                     max_price: 8000000,
                                     locality: "SG Highway" })
tool   ← { matched: 0, returned: 0, relaxable_filters: ["max_price"] }
model  → search_available_listings({ city: "Ahmedabad", bedrooms: 3,
                                     locality: "SG Highway",
                                     sort_by: "price_asc", limit: 5 })
tool   ← { matched: 18, returned: 5, rows: [ { price: 9200000, ... } ] }
model  → "Nothing on SG Highway at 3 BHK under 80 lakh right now.
          The closest is 92 lakh — want me to show those, or widen
          the area?"

Two things to notice. city: "Ahmedabad" reappears in turn 2 because the turn-1 tool call is in the replayed history — no filter state store, no slot machine, no merge logic. And the second call in turn 2 is the model reacting to relaxable_filters within a single turn, which is exactly the behaviour the loop buys you and the current pipeline cannot express at all.

§9 Conversation context

Decision — the message log is the state

Persist tool calls and tool results as chat_message rows and replay them. Do not auto-merge filters server-side. Sticky server-side filters are invisible to the model and to the customer, and become impossible to clear — “actually, anywhere in Gujarat” has to defeat a merge rule the model does not know exists. Re-emission from history is self-correcting: what the model can see, it can change.

Context assembly per turn, in order:

  1. System prompt — platform rules + chatbots.persona_prompt.
  2. Rolling summary of everything before the recent window, regenerated when the window slides.
  3. Last 8 turns verbatim, including tool calls with their arguments.
  4. Tool results: full JSON for the last 2 turns; older ones replaced by tool_result_summary (“returned 10 of 312 Ahmedabad listings”). Row payloads dominate the context budget and age badly — the call is what carries forward, not the rows.
  5. Working set, if non-empty (below).

working_set — deliberately small

A JSONB column on the session holding only what must survive summarization: the last successful query per data source, confirmed identity fields the customer has already given, and any pending confirmation token. It is a cache, not a source of truth — cleared on session close, never read by a validator, and reconstructible from the message log. Anything richer is a dialogue state machine, which is the industry-specific hardcoding this design exists to avoid.

§10 Validation and security

Ten gates, in order. Every tool execution passes all of them; none is skippable by tool type.

GateEnforcesOn failure
G1Tenancy bindingchatbot_id / company_id come from the server-side session. Model-supplied tenant identifiers are ignored, not merely validated.Drop + alert
G2Tool authorizationTool exists, is active, belongs to this chatbotError to model
G3Argument schemaJSON Schema 2020-12 against input_schemaError to model
G4Field exposureEvery referenced field is is_exposed on that data sourceError to model
G5Operator allowlistOperator is in that field's allowed_operatorsError to model
G6Type coercionValue casts to the declared type; enums matched exactlyError to model
G7LimitsRow cap, offset cap, filter-count cap, token capClamp silently
G8EgressAllowlist + resolved-IP check + pinned connect (§7.2)Drop + alert

G1 is the one that must never be relaxed. Every cross-tenant leak in a system shaped like this traces back to a tenant identifier that arrived as a tool argument. Treat model output as untrusted user input, because in a prompt-injection scenario that is precisely what it is.

Prompt injection through tool results

Retrieved chunks and fetched rows are content a tenant uploaded — or, in the rest_api case, content a third party returned. Wrap every tool result in an explicit data envelope, state in the system prompt that tool output is data and never instruction, and enforce the part that actually holds: no tool result can change tool availability, tenancy binding, or confirmation state. Those live in server state, so a successful injection can mislead a reply but cannot escalate a capability.

§11 Configuration UX

Adding an industry must be configuration, not a deploy. Six steps, all in the existing React dashboard:

  1. Knowledge — the current FAQ editor, plus document and URL upload. Chunking and embedding are background jobs with visible progress.
  2. Connect data — CSV upload first (covers most pilots), then REST and read-only SQL.
  3. Schema review — types inferred from a sample; the user confirms or corrects. Inference is a suggestion, never silently authoritative.
  4. Field permissions — the screen that matters. One row per field with toggles for exposed / filterable / sortable / returned, and operator chips. This is where internal_margin stays invisible.
  5. Actions — endpoint, method, parameters, credential, confirmation flag. A “send test request” button that shows the exact outbound call.
  6. Tool descriptions — name and description per tool, with a live “what the AI sees” panel rendering the compiled declaration.
Build the test console in the same phase

A test chat that shows every tool call, its validated arguments, the result, and the timing — inline, next to the conversation. Tool descriptions are prompt engineering whether or not you call them that, and a business user cannot write a good one blind. Without this screen every misconfigured bot becomes a support ticket you have to debug from logs; with it, the person who wrote the description can see it being ignored and fix it themselves.

§12 Scaling and operations

  • Redis channel layer. Prerequisite, not an optimization (F8).
  • Orchestration off the consumer. A turn is now seconds of model latency. The consumer enqueues; a worker runs the loop and publishes tokens back through the session group. This is also what makes multi-worker deployment possible at all.
  • Stream the final answer and emit a lightweight “checking our listings…” event when a tool starts, keyed off the tool's own description. Perceived latency is most of the UX here.
  • Move embedding out of the request path. MiniLM in-process is ~10ms but it is CPU-bound work inside an async consumer. Worker-side, or a small embedding service if you later want GPU batching.
  • Watch the dimension lock-in. vector(384) is a column type. embedding_model per chunk (§3.2) is what keeps a model upgrade from being a platform-wide outage.
  • Cost. Tool declarations are re-sent every round trip. Cache the compiled JSON, keep descriptions tight, and prune unused tools — a bot with 15 tools pays for all 15 on every call whether or not any is used.

§14 Open decisions

Six calls I would like made before implementation. My recommendation is on each, but the trade-offs are real.

D1

Introduce chatbots now, or keep company as the tenant key?

Adding it later means backfilling every tool, source, and conversation row.

→ Now. It is one table and one FK while the data is small.

D2

JSONB record store, or per-source physical tables?

JSONB: one code path, casts on filter. Physical: faster, runtime DDL.

→ JSONB, with the adapter seam that lets a big tenant migrate later.

D3

Flat parameters, or the raw filter IR as the model-facing schema?

Flat is more accurate and enforceable; IR is more expressive.

→ Flat, with opt-in advanced_filters for sources that need OR-groups.

D4

Bind to Gemini, or abstract the provider now?

Function-calling shapes differ enough that retrofitting is painful.

→ A thin adapter now: declarations in, calls out. A day's work, not a framework.

D5

Add a cross-encoder reranker to knowledge search?

Meaningfully better precision, ~50–150 ms and another model to host.

→ Not in v1. Ship RRF, measure with the §6.2 harness, revisit with data.

D6

Is handoff the model's decision or the server's?

Model judgement is better; a server rule is what breaks loops.

→ Both. Tool for intent, independent server rule as the safety net.

The measure of whether this worked is narrow and testable: onboarding a vertical nobody anticipated should touch no Python. If adding hotels, or clinics, or a used-car marketplace requires a new executor, a new branch, or a new prompt template, the abstraction has leaked and the fix belongs in the registry, not in the orchestrator.
